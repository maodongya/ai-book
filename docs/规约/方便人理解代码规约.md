# 方便人理解代码规约

目标：让半年后的自己、同事或 AI 打开文件后，**不用猜**就能回答三件事：这段代码做什么、怎么用、依赖什么。

本规约服务于阅读，不替代编译器或格式化工具。能编译只说明机器能跑；能读懂才说明人能改。给人看的注释用简体中文（见第 4 节），名字仍用完整英文。

---

## 1. 先写清边界

一个文件、一个类型只承担一件读者能用一句话说清的职责。

| 好的边界 | 难读的边界 |
|----------|------------|
| `TranslationPromptBuilder` 只拼提示词 | 一个 3000 行 ViewModel 里夹杂提示词、解析、UI 文案 |
| `TranslationTargetLanguage` 只管枚举、迁移、解析 | 把语言解析写进按钮的 `action` 里 |
| `BookL10n` 只取文案 | 业务逻辑里散落中英日硬编码字符串 |

判断标准：

- 不看实现，也能从类型名知道它做什么。
- 改内部算法，调用方不必跟着改。
- **单个类型（`class` / `struct` / `enum` / `actor`）不超过 800 行**（含空行与中文注释）。到 800 行必须按职责拆出去，禁止继续往里堆方法。
- 文件变大时，优先按职责拆文件，而不是按「技术层」机械分层；不要靠删注释、挤进同一文件的多个类型、或把逻辑塞进 extension 来绕开 800 行上限。同一类型散落在多个 extension 文件里的行数**加总**仍不得超过 800。

### 1.1 何时拆类型

有下面任一信号就拆，不要等超过 800 行才动手：

| 信号 | 拆法 |
|------|------|
| 改 A 功能必须翻过 B 功能的代码 | 按**变更原因**拆：提示词、解析、对齐、存储各成一类 |
| 值对象和读写混在一起 | 值用 `TranslationTargetLanguage`，读写用 `…Store` |
| UI 布局和产品规则写在同一类型 | 规则进可单测类型，View 只绑已有属性 |
| 一段流水线有独立词汇（分段、锚点、对齐） | 按**步骤**拆：`ParagraphSegmenter` / `AnchorResolver` / `Aligner` |
| 无状态算法被多个调用方复制 | 抽 `enum` 命名空间（如 `TranslationAligner`），不要空壳 `class` |
| 嵌套类型已经能单独起一个读者能懂的名字 | 升成同包下的独立文件 |

不要拆的情况：只有十几个属性的配置、仅为一个类型服务且不足一屏的 `private` 辅助、还说不清职责的「Utils / Helper / Common」。

拆完后每个新类型仍要能用一句话说清；调用方只依赖公开签名，不依赖被拆出去的内部步骤。

### 1.2 何时拆文件与包

- **一个文件一个主类型**，文件名与主类型一致。同文件只允许放该类型的紧密附属（例如值与其 `Store`，且合计仍宜短）。
- **文件夹 = 一个读者能叫出名字的能力**（翻译、风格、目录浏览），不是「第 N 层」或「各种工具」。
- 同一能力出现 **3 个及以上** 主类型时，建子目录（如 `Reading/Translation`、`UI/Style`）；只有一两个文件先放在父目录，不要提前空文件夹。
- **SPM target 是包**：可独立编译、可被测试引用。新 target 只在「无 UI、可单独测、AIBook 只编排不实现」时才加（现有先例：`AIBookEvolution`）。
- 依赖单向：界面与编排可以依赖 `Core` / `Persistence` / `AIBookEvolution`；**领域与进化库不得反向依赖** `App`、`UI`、`Reading`。禁止 `Utils`、`Common`、`Helpers`、`Misc` 这种收纳箱目录。
- 新功能先问「放进哪个已有包」；只有一句话概括不了现有任何一包时，才新建目录，并在该目录写 `功能说明.md`。

### 1.3 包功能说明写在文件夹里

各包做什么、不做什么、典型入口，写在**该目录自己的** `功能说明.md`，不写进本规约。打开文件夹先读这一份。

- SPM target 根目录（`Sources/AIBook`、`Sources/AIBookEvolution`、`Tests/AIBookEvolutionTests`、`Tests/AIBookL10nTests`）和每个功能子目录都要有。
- 固定写清：做什么、不做什么、典型入口；有子目录时列出并链到子目录的 `功能说明.md`。
- 新增、挪走或改职责时，同步改对应 `功能说明.md`。不要把正文再抄回本规约。源码旁的 `功能说明.md` **不搬进** `docs/`。
- 新增文件必须落在对口包，不要图方便扔进 `Core` 或 `Reading` 根下。

依赖方向（读者按箭头找代码，不要逆行新增引用）：

```
App → UI / Reading / Speech / LLM / Cursor / Evolution
      → Core / Persistence
AIBook（编排）→ AIBookEvolution（纯领域）
```

## 2. 名字说人话

名称要让读者读出**业务含义**，不要读出实现细节。

**类型与文件**

- 用完整英文词：`TranslationTargetLanguage`，不要 `TTL`、`TLang`。
- 文件名与主类型一致：`BookAppLanguage.swift` 里是 `BookAppLanguage`。
- 无状态工具用 `enum` 命名空间（如 `BookL10n`、`TranslationAligner`），避免「空壳 class」。
- 存储与值对象分开：`TranslationTargetLanguage` 是值，`TranslationTargetLanguageStore` 是读写。

**函数与属性**

- 动词 + 对象：`migrated(from:)`、`resolved(appLanguage:)`、`build(...)`。
- 布尔名用是非判断：`isStale`、`canAlignTranslationWithSource`，不要 `staleFlag`。
- 解析/回退写在名字里：`migrated` 表示旧值或坏值会变成默认值，读者不必翻实现。

**避免**

- `data`、`info`、`helper`、`manager2`、`doStuff`。
- 同一概念两个名字（例如一边叫 `lessonPlan`，一边叫 `translation`）。新代码统一用当前产品词：讲解、翻译、进化；历史别名只在迁移函数里出现一次。

## 3. 控制流要直

人按从上到下读。把「先失败、再干活」写清楚。

```swift
// 好：入口处拦住，后面全是正常路径
guard let stored, !stored.isEmpty else { return .followAppLanguage }
return TranslationTargetLanguage(rawValue: stored) ?? .followAppLanguage
```

```swift
// 差：嵌套 if，读者要在脑子里记一堆分支
if stored != nil {
    if !stored!.isEmpty {
        if let language = TranslationTargetLanguage(rawValue: stored!) {
            return language
        }
    }
}
return .followAppLanguage
```

约定：

- 优先 `guard` / 提前返回，少写深层 `if`。
- `switch` 写全枚举，不要默认分支悄悄吞掉新 case。
- 一个函数只做一种抽象层次：要么编排调用，要么做具体计算，不要混在一起。
- 公共函数放上面，`private` 辅助放下面；读者先看到用法。

## 4. 注释用中文，写「为什么」，不写「又说了一遍代码」

标识符保持英文（类型、函数、文件名见第 2 节）。**给人看的注释一律简体中文**：`//`、`///`、`/* */` 以及测试里解释断言意图的注释。英文注释只保留在必须引用外部协议原文的地方（例如 JSON 字段名、BCP-47 标签），其余说明仍用中文。

该写中文注释的情况：

- 类型或文件顶部用**一句** `///` 交代职责，读者不用猜这个类型管什么。
- 不直观的产品规则（切换目标语言**不**重译当前译文）。
- 与界面语言不一致的行为（提示词可用中文，但目标语言必须写死 BCP-47）。
- 历史兼容（`fromPersisted` 仍接受旧的中文标题）。
- 不变量：`precondition(targetLanguage != .followAppLanguage)` 旁边说明「调用前必须先 resolved」。
- 新增或改过的公开 API、非显而易见的分支、回退与迁移：改完就补中文注释，不要等以后「有空再写」。

不该写的注释（中文复述代码同样禁止）：

```swift
// 遍历所有语言  ← 代码已经写了 for language in ...
```

好的例子：

```swift
/// 右页翻译区（逐字 / 整段）专用 persona，与读书讲解、名著补充分离。
enum TranslationAssistant { ... }

// 切换目标语言不重译当前页：已有译文留给用户对照，下次翻译再按新语言走。
```

## 5. 状态从哪来、到哪去，要一眼能追

AIBook 里状态容易散。读者必须能顺着一条线走：

1. 用户改设置 → `AppSettings` 发布并写入 `UserDefaults`。
2. 发起翻译 → `ReadingViewModel` **当场**读取 `resolvedTranslationTargetLanguage`。
3. 拼提示词 → `TranslationPromptBuilder`，不回头改已有译文。

约定：

- 持久化键集中定义（`TranslationTargetLanguageStore.key`、`AppSettings.Keys`），不要在多处写死 `"aiBook.xxx"`。
- 「跟随界面语言」在**使用时**解析，不要在用户点选时把值拷成具体语言；否则读者会以为改界面语言不会影响下次翻译。
- 单例（`AppSettings.shared`）只做配置与偏好，不要再往里面塞翻译对齐、翻页、会话。
- UI 只绑定已有属性，不要在 `Button` 里偷偷改第二份状态。

## 6. UI 与领域分开读

读者打开 SwiftUI 文件，应只看到「怎么摆、绑哪个值」。领域规则应在可单测的类型里。

| 放在 UI | 放在领域 / ViewModel |
|---------|----------------------|
| Picker、菜单勾选、帮助文案 | 语言迁移、系统 Locale 回退 |
| 全屏按钮图标与快捷键 | `LearningPaneFocus` 与系统全屏切换 |
| `BookL10n.string("translation.target.title")` | 提示词里的目标语言合同 |

界面字符串一律走 `BookL10n` 与 String Catalog，不要在 View 里新写死中文（提示词、测试夹具除外）。新增键时同时补八种界面语言，并跑目录测试。

控件复用优先：翻译目标语言在设置页和「翻译操作」菜单共用同一个 `AppSettings` 属性，不要做两套默认值。

## 7. 数据形状保持稳定、可见

对外协议（JSON 字段、`UserDefaults` rawValue、对齐结构）改动成本高，读者需要看见「哪些不能随便改」。

- 枚举带稳定 `rawValue`（`zh-Hans`），并写 `migrated(from:)` 处理空值、乱值。
- 翻译输出 JSON 字段名保持英文且不变；提示词里明确写「JSON 字段名保持不变」。
- 旧文件、旧会话没有新字段时，解码用默认值（如 `decodeIfPresent ... ?? 0`），并在测试里锁住。

能用值类型就用值类型（`struct` / `enum`）。需要引用语义或发布变化时再用 `class` + `@Published`，并标 `@MainActor`。

## 8. 测试是给人看的说明书

测试名写成行为，不要写成 `test1`。

好的例子：

- `testMissingAndInvalidStoredValuesFollowAppLanguage`
- `testSimplifiedChineseRequiresModernVernacularForClassicalChinese`
- `testBothModesCarryTheSameTargetLanguageContract`

约定：

- 一个测试只证明一件事；名字里出现「and」就考虑拆开。
- 断言可读的结果（提示词里有 `el`、有「现代白话文」），不要断言内部私有步骤。
- 持久化测试用独立 `UserDefaults(suiteName:)`，测完删掉，避免污染开发机设置。
- 改行为时先改测试名和断言，让失败信息指向产品规则。

## 9. 规约与设计文档放在 `docs/`，按能力分目录

规约、产品设计、UI、阅读、进化等**给人读的长期文档**一律放在仓库 `docs/`（不要另建根目录 `doc/`，避免两套文档树）。禁止在仓库根目录新增长期 `.md`（`README.md` 除外）。目录索引见 [`docs/README.md`](../README.md)。

| 目录 | 放什么 | 不放什么 |
|------|--------|----------|
| `docs/规约/` | 代码与文档怎么写（本文件） | 某功能的产品设计正文 |
| `docs/产品/` | 整体功能设计、给用户的说明书 | 实现计划、Swift 注释 |
| `docs/UI/` | 整体界面设计、风格与主题 | 阅读翻页算法、进化队列语义 |
| `docs/阅读/` | 阅读模式、同步滑动 / 翻页 | 设置页布局、进化分析 |
| `docs/进化/` | 进化设计与实现计划 | 读书双页交互 |
| `docs/superpowers/` | 单次专题的 spec / plan | 已稳定、应归入上面各目录的长期设计 |

拆分规则：

- **一个子目录 = 一类读者问题**（「产品是什么」「界面怎么摆」「阅读怎么翻」「进化怎么升级」「代码怎么写」）。
- 同一能力出现第二份长期文档时放进已有子目录，不要再堆到 `docs/` 根上。
- 只有现有子目录一句话概括不了时，才在 `docs/` 下新建子目录，并改 `docs/README.md` 与本节表格。
- 单次任务的规格放 `docs/superpowers/specs/` 与 `plans/`；任务结束后若规则仍有效，把结论收进对应长期文档，不要只留在 plan 里。
- 源码目录的 `功能说明.md` 跟着代码走（见 1.3）。`功能说明书.md` 以 `docs/产品/` 为仓库正文，并同步 `Sources/AIBook/Resources/功能说明书.md` 供打包。

## 10. 改代码必须同步改设计文档

行为、界面、协议或包职责一变，**同一份 diff / 同一次提交**里改对应设计文档。禁止先合代码、文档「过后再补」；读者只看文档会得出与代码相反的结论，就等于没改完。

按改动选文档，改到写对为止，不要无关章节顺手重写：

| 改了什么 | 必须同步的文档 |
|----------|----------------|
| 产品能力、主流程、用户能感知的行为 | `docs/产品/整体功能文档设计.md`；面向用户的说明改 `docs/产品/功能说明书.md`，并同步 `Sources/AIBook/Resources/功能说明书.md` |
| 窗口、工具栏、双页、设置页等界面 | `docs/UI/整体UI文档设计.md`；风格令牌与预设另改 `docs/UI/aibook风格.md` |
| 阅读模式、翻页、左右页联动 | `docs/阅读/aibook阅读模式.md`；滚动/翻页专项另改 `docs/阅读/同步滑动翻页设计.md` |
| 进化分析、队列、自动升级 | `docs/进化/aibook进化设计.md`；落地步骤另改 `docs/进化/aibook进化实现计划.md` |
| 某目录职责、入口、依赖方向 | 该源码目录的 `功能说明.md`（见 1.3） |
| 已有专题规格 | `docs/superpowers/specs/` 或 `plans/` 里仍有效的那份，避免与实现各说各话 |

纯重命名、格式化、或与文档描述无关的缺陷修复：若文档没有因此说错，可以不改设计文档；**只要文档里有一句会过时，就必须改。** 新能力若没有任何设计文档能接住，先补文档再写代码，或与代码同一提交新增文档。

提交说明写清「代码 + 文档」各改了哪条产品规则，不要只列文件名。

## 11. 少即是清晰

不要为「将来可能」增加读者必须跳过的代码。

- 不需要的协议、泛型、回调、配置对象一律不写。
- 不复制粘贴「类似 Task N」的第二套逻辑；公共规则抽一个函数。
- 不在修复 A 时顺手重构 B；无关 diff 会让审查者找不到真正改了什么。
- 提交说明写原因，不写文件清单。人先读 commit message，再读 diff。

## 12. 阅读检查清单

改完或审查时，用下面几问过一遍：

1. 文件名和类型名能否当目录用？任一类型是否超过 800 行？新文件是否落在对口包？该包 `功能说明.md` 是否仍准确？
2. 公开函数是否只需看签名就能调用？该拆的类型是否已按职责拆开、而不是只拆文件名？
3. 失败路径是否在函数开头被拦下？
4. 持久化键、默认值和非法值回退是否只在一处？
5. UI 是否只展示、不偷偷实现规则？依赖是否仍单向（领域不引用 App/UI）？
6. 该写的注释是否都是简体中文，且只解释非显而易见的「为什么」？
7. 测试名是否能当需求条目读？
8. 这次 diff 是否只做一件读者能概括的事？新文档是否落在 `docs/` 对口子目录？对照第 10 节，过时的设计文档是否已在同一提交改完？

任一项要解释很久，就先改结构或改名字，再继续加功能。
